# ALDOL MCP Forge Studio — implementation and verification

Baseline: main `c33d6c1ab8066b90ec644bd19fe6516fdc0d4630`, PR #4 merged. PR #5 remains a separate Draft and is not required or deployed by this change.

## Implemented

Five responsive Korean screens: dashboard, natural-language/OpenAPI creator, schema/code editor with additive immutable versions and side-by-side comparison, MCP validation lab, ZIP export. Dark navy/teal, semantic navigation, labels, keyboard focus, live error notices. Browser-local storage stores only selected project ID; actual project records/files belong in authenticated R2.

Existing three MCP read-only contracts remain unchanged in `worker/core.js`. Browser `/api/rpc` uses those same MCP handlers, not mock responses. Keyword routing is explicitly labelled, not represented as LLM reasoning. Unsupported requests do not generate unrelated projects.

Worker-native generation includes exact original curated Python source assets, generated SDK-v2 entrypoints, schema manifests, requirements, README, client config, checksum list and ZIP. HTML/JSON/text templates and bounded OpenAPI GET import supported. Generated Python is never executed/evaluated in the Worker. Test/SDK statuses are explicit SKIP where not run.

R2 holds immutable project JSON including metadata and file contents. Site-scoped platform user ID determines a SHA-256 owner prefix; UUID IDs and conditional name reservations prevent path injection and overwrite. Add tool creates a new revision; no delete/publish/merge endpoint. D1 was assessed but is unnecessary for this bounded document model; not provisioned. ZIPs are produced on demand, not publicly shared.

The five new MCP tools have a Sites-specific project UUID interface; they are not drop-in equivalents of the original filesystem-based write tool responses. `forge_test` is checksum-only, NOT a Python execution substitute. `forge_package` really creates ZIP bytes and returns a private download path/hash.

## Security and live boundary evidence

Existing Site project `appgprj_6ad6bde7a48881918c1767e3e9f1252f`, unchanged origin and owner-only access. Initial version 2. Version 3 deployed successfully as source `67b381a74b023ca1ff274197f2dda0d68ec58df2` with write gate OFF.

Read-only plugin tools were called successfully before/after deployment. Production Worker logs show authenticated MCP identity forwarding (`authenticated: true`) without recording identity values. The owner-private service readback returned `/api/session` HTTP 200, `storage: R2`, `local_qa: false`, `authenticated: false`. This confirms the service bypass credential does not impersonate a user. No spoofed identity headers were sent to production. A browser-rendering service invocation forwarded verified email but no user ID; the app correctly refuses writes for missing ID. Normal browser user identity must be checked separately from MCP identity.

After platform MCP identity forwarding and R2 binding were confirmed, the server write flag was set. Every actual operation still requires platform user ID. No user ID is accepted in arguments. A live user read/write/ZIP round trip is distinct from local tests and must not be inferred from successful deployment or an R2 binding alone.

## Remaining limitations

No arbitrary-code generation, free-form code/schema edits, OpenAPI operation editing, API auth/write methods, Python execution engine, external deployment, background jobs, GitHub account requirement, or automatic PR merge. OpenAPI generation additionally requires string descriptions while original preview accepts its original wider representation.

Production UI and live MCP write verification are separate gates. Existing connected plugin may require a fresh conversation to expose its refreshed five tool definitions. If browser Sites user ID is absent, writes stay disabled instead of using email as a surrogate ID.
