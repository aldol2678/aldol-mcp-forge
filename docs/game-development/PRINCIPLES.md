# ALDOL Studio | 공통 게임 개발 원칙 (v0.1)

> 상태: **CURRENT (`main` 반영본 기준)** · 작성 및 사용자 채택 승인: 2026-10-24 · 적용 범위: ALDOL이 개발하는 게임 전반  
> 공식 적용은 이 문서가 **`main`에 병합된 때부터** 시작한다. 별도 브랜치·PR의 미병합 변경은 제안일 뿐이다.

## 목적과 경계

게임을 빠르게 **만드는 것**과 플레이어에게 **재미있는 것**을 구별한다. AI를 활용한 생산성은 이 구별을 없애지 않는다. 이 문서는 장르·플랫폼·출시 규모와 무관하게 적용할 기본 질문을 담으며, 개별 게임의 콘셉트·확정된 디자인·보안·접근성·안전·운영 계약을 임의로 뒤집지 않는다.

## 제1원칙: 핵심 재미 보존 (CORE FUN FIRST)

**"무엇을 더하면 재미있을까?" 이전에 "이걸 빼도 재미있는가?"를 묻는다.**

1. 플레이어가 반복하고 싶은 **핵심 행동과 보상**을 한두 문장으로 정의한다. 재미의 근거가 미확인이라면 *가설*로 표시한다.
2. 새 기능이 없어도 그 핵심 행동 자체가 즐거운지 작은 프로토타입과 실제 플레이로 확인한다.
3. 추가 기능의 가치는 **핵심 재미 강화**, **플레이 장애 해소**, **필수 품질·안전 확보** 중 무엇인지 명시한다.
4. 재미에 기여하지 않으면서 선택·학습·관리 비용을 늘리는 요소는 축소·통합·제거를 우선 검토한다.
5. 제거가 저장 데이터·진행도·호환성에 영향을 주면 바로 삭제하지 말고 이전·보존·복구 계획을 선행한다.

> 제거 질문은 사고 도구이지 모든 시스템을 삭제하라는 명령이 아니다. 접근성, 저장 안정성, 법적 준수, 보안과 같은 필수 요소는 직접적인 '재미 점수'가 없어도 유지한다.

| G-002 | **가설과 검증 구분** | AI의 아이디어, 구현 성공, 자동 테스트 PASS를 '재미 입증'으로 바꾸지 않는다. 플레이 관찰·피드백과 테스트 조건을 남긴다. |
| G-003 | **추가 전에 단순화** | 신규 기능 제안 시 제거·통합·기존 기능 개선 대안을 최소 1개 비교한다. |
| G-004 | **선택의 의미 보존** | 수량 증가보다 새로운 결정, 이해 가능한 피드백, 유효한 전략 다양성을 우선한다. |
| G-005 | **플랫폼 맞춤 UX** | 모바일 우선 프로젝트는 작은 화면·터치·접근성·가독성을 먼저 검증하고, 각 게임의 실제 주력 플랫폼을 존중한다. |
| G-006 | **진행도·데이터 보호** | 기존 저장·진행·경제·콘텐츠와 호환성을 확인한다. 변경이 필요하면 이전·백업·롤백 경계를 밝힌다. |
| G-007 | **작은 실험과 명확한 되돌림** | 핵심 재미에 관한 불확실성이 클수록 작은 플레이 가능한 실험으로 시작한다. 운영 서비스·기존 출시물을 기본적으로 보존한다. |
| G-008 | **검증 가능한 보고** | 실행됨, 테스트됨, 실제 플레이에서 확인됨, 출시 승인됨을 별도로 기록한다. 미검증을 PASS로 표기하지 않는다. |

## 신규 기능 / 패치 판단 게이트

패치 제안에는 아래 질문에 짧게라도 답한다. 모든 아이디어에 긴 보고서를 요구하지 않는다.

1. **핵심 루프:** 이번 변경이 어떤 플레이 행동·선택·보상을 더 좋게 만드는가?
2. **제거 대안:** 무엇을 빼거나 합치면 같은 효과를 더 단순하게 얻을 수 있는가?
3. **검증 계획:** 플레이어가 직접 확인할 행동 지표·관찰 질문은 무엇인가? (예: 반복 플레이 의향, 혼란 구간, 선택 다양성)
4. **유지비/위험:** 구현·운영·학습·UI 복잡도, 저장/호환성, 모바일, 기존 콘텐츠에 미치는 비용은 얼마인가?
5. **판정:** `실험` / `수정·단순화` / `추가` / `보류` / `제거 후보` 중 하나를 제안하고 근거 수준을 쓴다.

버그 수정·보안·접근성·데이터 복구 등 **필수 품질 변경**은 재미 검증을 기다리지 않는다. 단, 기존 플레이 회귀와 사용자 영향은 검증한다.

## 플레이 검증의 최소 기록

- 대상 게임 / 빌드·버전 / 플랫폼·기기 / 관찰 일시
- 검증하려는 **핵심 재미 가설**과 수행한 플레이 시나리오
- 관찰 사실(성공·실패·혼란·반복 행동)과 개인적 해석을 분리
- 새 기능의 체감 가치 및 제거·단순화 가능성
- 결과 상태: **완료·검증됨 / 실행됨·검증 미완료 / 실패 / 미확인** 중 실제 근거에 맞는 표기
- 다음 변경안과 되돌림·저장 호환성 여부

자동 테스트와 CI는 안정성·회귀에 관한 증거다. 별도의 플레이 검증 없이 재미 검증으로 대체하지 않는다. 봇이나 AI의 시뮬레이션 플레이 역시 실제 사람의 플레이와 구분한다.

## 게임별 적용 예시 (검증 전 가설)

| 게임 | 검증할 중심 경험 | 확장 시 주의점 |
| --- | --- | --- |
| 겸직금지 | 현실·판타지 융합 직업과 카드·유물 조합을 통한 의미 있는 전투 선택 및 성장의 만족감 | 카드·유물의 수만 늘고 선택의 전략적 차이는 작아지지 않는가 |
| 시간복제 공장 | 과거의 나와 협력해 자동화를 완성하는 만족감 | 반복 작업만 늘리고 협력 선택은 늘지 않는가 |
| 꼬마 군단 원정대 | 부대 구성·성장·전투 판단의 만족감 | 유물·스탯이 늘어도 선택 차이가 느껴지는가 |
| 한가람 | 시대·규모·존재의 변화가 만드는 탐험과 발견 | 이동·탐색보다 시스템 관리가 무거워지지 않는가 |
| INHA WORLD | 월드 안에서의 발견·활동·교류 경험 | 기능이 서로 단절되고 기본 경험을 가리지 않는가 |

이 표는 **게임별 디자인 확정이나 실제 재미 검증 결과가 아니다.** 해당 프로젝트의 현행 기획과 플레이 결과를 우선 확인한다.

## AI 협업과 의사결정

- AI는 설계 대안·프로토타입·코드·자동 테스트·사용성 가설을 제시할 수 있지만, 인간 플레이테스트 없이 '재미가 증명됐다'고 결론 내리지 않는다.
- 기능 목록과 개발량은 진행 지표일 수 있어도 **재미의 대리지표**로 사용하지 않는다.
- 프로젝트별 승인된 결정, 안전·보안·규정, 배포 게이트가 우선한다. 이 원칙은 권한·병합·배포의 자동 승인이 아니다.
- 사용자 승인 없이 프로덕션 변경·저장 데이터 파괴·출시·정본 승격을 하지 않는다.

## 개정과 상속

- 공통 원칙 개정: 변경 이유, 영향을 받는 게임, 제거 대안, 검증 근거를 PR에 남기고 사용자 승인 후 반영한다.
- 개별 게임은 공통 원칙을 **참조**하고 특성상 다른 선택이 필요한 경우 게임별 문서에 이유와 범위를 기록한다.
- Notion은 **목차·열람 허브**로 사용하고 원칙 본문을 복제해 독립 정본으로 관리하지 않는다.
- 다른 저장소의 AI는 이 문서를 자동으로 가져오지 않는다. 해당 프로젝트의 `AGENTS.md`나 작업 지침에 정본 링크와 핵심 게이트를 **별도로 연결**한다.

이 문서는 원칙의 시작점이다. 규칙과 문서를 늘리는 일 자체가 목적이 아니다.
